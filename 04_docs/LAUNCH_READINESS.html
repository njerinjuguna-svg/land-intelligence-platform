What's left to launch

The intelligence is largely built. What is missing is mostly the thing a client installs, somewhere for it to run, and the paperwork that makes it sellable — and one of those three is further behind than it looks.

Built and verified

Roughly nine months of the hard part.

  • 30 ETL pipelines, 12 schema migrations
  • Enrichment engine — 43 assertions passing
  • Suitability scoring — 71 checks, 4 of 20 parcels correctly refused
  • Embed API: key auth, row-level scoping, geometry firewall, usage logging
  • PDF generator, versioned and reproducible
  • Buyer page design settled and agreed

Not yet built

Smaller than the above. Not small.

  • The embed script itself — v1.js
  • Any server. It runs on one laptop.
  • Client onboarding with rejection gates
  • Rate limiting and billing
  • 4 drafted letters, unsent; 1 not drafted
  • A price

The one that should worry you most

The whole architecture is "two lines in the client's page", and those two lines point at a file that does not exist. 06_delivery/ holds three Python files and nothing else — no v1.js, no server config, no deployment.

The API works. It works on 127.0.0.1 on your machine, reachable by nothing. Every demo so far has been you running uvicorn in a PowerShell window. A client cannot buy that. It is not a large job — a loader script, a host, a domain, TLS — but it is the difference between a project and a product, and nothing else on this list matters until it is done.

1. The deliverable

Build

What a paying client actually receives. This is the shortest section and the most urgent.

v1.js — the embed loader

Not started

Reads data-plot-ref and data-key off the script tag, calls /v1/plots/{ref}/embed, injects the returned HTML into the host page. Handles the plot-not-found and key-rejected cases without breaking the client's layout.

Small — an afternoon. It is item one because everything downstream assumes it.

Somewhere to run

Not started

A host, a domain, TLS, the database migrated off the laptop, backups, and something that restarts uvicorn when it dies. Checklist E10 flags this as blocking: diff the schema snapshot against the versioned SQL files before migrating, because the database could not be rebuilt from its own files once already and only the snapshot caught it.

Rate limiting and usage billing

Not started

clients.subscriptions and clients.api_usage exist and the API already writes usage rows. Nothing reads them, and nothing stops a client calling a million times.

The map on the buyer page

Decided, not built

Google Maps satellite tile with the plot boundary drawn over it, plus Street View where coverage exists. Needs a Cloud key with billing enabled. The boundary is the seller's own survey data, so nothing is licensed from anyone else — this was mistakenly thought blocked by B4, which only ever applied to the PDF.

2. Getting a client's plots in

Build

A loader exists and has ingested real KMZ. What it does not do is refuse bad input — and this test set already contains two examples of input it should have refused.

Upload rejection gates

Detected, not enforced

PLOT-1069 and PLOT-1070 are one polygon under two references — either a drafting duplicate or the same ground sold twice. PLOT-950 reads slope 14.38° against a project median of 3.00°, which neighbouring plots in one subdivision do not do; the repair at load probably moved it onto ground that is not the plot.

The verifier catches both, after enrichment. The upload must reject them before a buyer ever sees a report. Same principle as everywhere else in this build: a rule you have to remember is a reminder, a rule the code cannot proceed without is a control.

parcel_ref mapping, and keeping status current

Not started

Their site says "Plot 457", the database says parcel_ref. Agreed once at onboarding. Listing status is the second handshake and it never stops — the availability panel is the strongest sales feature on the page and it goes stale silently. Today all eight Oak Grove plots read available and every price is null.

3. Legal

Blocks selling

Five letters drafted in 04_docs/correspondence/. One sent. This is the long pole and has been for four sessions — not because it is hard, but because it is waiting on other people, which means starting it early is the whole trick.

A1 — WDPA is non-commercial

Send the KWS letter

Powers in_protected_area on 19 of 20 parcels — a field that can refuse to score land entirely. The cheapest high-value move on the board: it closes A1 and replaces a coarse boundary that currently blocks saleable land near park edges.

A2 — CA coverage has no declared licence

Sent, awaiting reply

Told verbally that no licence is needed. Do not close on that. "Someone said so on the phone" is not an answer to a client or an acquirer. Same thread carries B1 and B1b — the two operator layers that are byte-for-byte the same data.

A3 — OpenCellID is share-alike

Price the commercial licence

The one you can pay your way out of. Unwired Labs sell commercial licences; it may cost less than engineering a replacement, and it closes outright.

A5, B7 — Kenya Power and WASREB

1 drafted, 1 to draft

Electricity and water/sewer distance. Neither has a free fallback — both are buried or unmapped infrastructure, so OSM has effectively nothing. Letter or nothing.

A4 — ODbL share-alike

Contained by design

The embed architecture already answers this: the client receives values and pictures, never geometry. riparian_buffers remains the one high-exposure item because it is derived geometry and therefore unambiguously a database — it must never be handed out.

4. Judgement calls only you can make

Decide

No amount of engineering settles these, and two of them shape what the product is.

B5 — what the platform says about title

Open

Say nothing, say plainly what we do not do, or integrate an advocate's search as a paid step. In this market it is the claim a buyer trusts most and the one most likely to end in court. No "Verified" badge on any page until this is decided.

Price, and what a subscription buys

Open

Per plot, per scheme, per month, per report download? The billing code cannot be written until this is answered, and the client agreement cannot be drafted either.

The model does not separate neighbours

Known, unresolved

All seven Oak Grove plots score 94–98 residential. Neighbours should be similar — but that tight a band at the top means the model is not discriminating between plots in one scheme, which is exactly the comparison a buyer in that scheme is making. Either find a within-scheme signal, or say plainly that the score is about the area and the differences are size and price.

The critical path to one paying client

Ordered by what unblocks what, not by size.

  1. Send the four unsent letters this week

    KWS, Kenya Power, WRA, KNBS — plus draft WASREB. They are written and sitting in a folder.

    They wait on other people. Everything else waits on you, so these go first regardless of what else is happening.

  2. Write v1.js and deploy somewhere real

    Loader, host, domain, TLS, database off the laptop. Snapshot-diff the schema before migrating.

    Until this exists there is nothing to sell, and no demo that survives you closing your laptop.

  3. Add the upload rejection gates

    Duplicate geometry and boundary confidence, refused at load rather than flagged after enrichment.

    The first client's data will be worse than Oak Grove's, and Oak Grove already has two bad parcels in eight.

  4. Decide title and price

    B5 and the commercial model. Both block the client agreement.

  5. Run one client end to end

    Their KMZ in, their plots scored, the widget live on their page, one PDF sold.

    Everything before this is preparation. This is the first evidence that any of it works.
